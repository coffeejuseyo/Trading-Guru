## 📖 開場故事：自動化工廠的生產線

一家麵包工廠決定自動化，把生產線分成幾個站：

1. **原料站**：每天早上收麵粉、雞蛋、奶油，**先檢查品質**（發霉的退回）
2. **配方站**：依照食譜決定今天要做什麼、做多少
3. **品管站**：檢查配方站的決定是否合理（例如「今天做 10 萬個麵包」——等一下，倉庫放不下！）
4. **烘焙站**：真正把麵包烤出來
5. **監控室**：螢幕上顯示每一站的狀態，有異常就響警報；必要時**按下緊急停止按鈕**

每一站各自獨立：換一個麵粉供應商，只要改原料站；換一份食譜，只要改配方站。

> 🏭 **自動化交易系統就是這條生產線**：資料（原料）→ 訊號（配方）→ 風控（品管）→ 下單（烘焙）→ 監控（監控室）。每個模組各司其職，出了問題才知道是哪一站壞掉。而監控室裡的**緊急停止按鈕**，可能是整個系統最重要的零件。

## 🧠 正文

### 1. ⭐ 五個模組

```
  ┌──────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
  │ ① 資料    │ → │ ② 訊號    │ → │ ③ 風控    │ → │ ④ 下單    │
  │ 取得、清理 │   │ 策略規則   │   │ 部位、上限 │   │ 券商介面   │
  │ 檢查       │   │ 目標部位   │   │ 停機開關   │   │ 成交回報   │
  └──────────┘   └──────────┘   └──────────┘   └──────────┘
        └──────────────┴──────────────┴──────────────┘
                              ↓
                     ┌──────────────────┐
                     │ ⑤ 監控與紀錄       │
                     │ 日誌、警報、報表    │
                     └──────────────────┘
```

| 模組 | 負責什麼 | 對應單元 |
|---|---|---|
| **① 資料** | 取得最新資料、清理、**檢查**（缺值、異常、時間） | 9.10、9.11 |
| **② 訊號** | 執行策略規則，產生「目標部位」 | 8.13、10.2 |
| **③ 風控** | 檢查部位大小、總風險、回撤上限；**停機開關** | 6.4、6.10 |
| **④ 下單** | 把目標部位轉成委託、送出、確認成交 | 2.2 |
| **⑤ 監控與紀錄** | 記錄每一步、異常時發出警報、產生每日報表 | 7.6 |

> 🔑 **為什麼要分開？** 回測時用的「資料」和「訊號」模組，可以**原封不動**地用在實盤——只要把「模擬下單」換成「真實券商」。這大幅降低了「回測和實盤的程式不一樣」造成的錯誤。

### 2. ⭐ 紙上交易骨架程式

[`code/paper_trading_skeleton.py`](code/paper_trading_skeleton.py) 用不到 150 行，實作了五個模組（只做紙上交易，不會連接任何券商）：

| 類別 / 函式 | 模組 | 重點 |
|---|---|---|
| `DataFeed` | ① 資料 | 一天一天提供資料，**每天只給到今天為止**（避免偷看未來） |
| `MaStrategy` | ② 訊號 | MA50 > MA200 → 目標部位 1，否則 0 |
| `RiskManager` | ③ 風控 | 帳戶回撤超過上限 → **停機**，並平倉 |
| `PaperBroker` | ④ 下單 | 收盤後送出委託、隔天開盤成交；**防止重複下單**；扣成本 |
| `run()` 與 `logging` | ⑤ 監控 | 主迴圈；每筆成交與警告都寫進日誌 |

主迴圈的順序，和 10.3 的事件驅動回測一樣：

```py
for date, history in feed:
    broker.execute_at_open(date, today["Open"])     # ① 開盤：執行昨天的委託
    equity = broker.equity(today["Close"])          # ② 收盤：計算資產
    if not risk.check(equity):                      # ③ 風控：超過回撤上限就停機
        ...
    target = strategy.target_position(history)      # ④ 產生訊號 → 送出明天的委託
```

### 3. 執行：有停機開關 vs. 沒有停機開關

```python
from paper_trading_skeleton import run

curve, broker = run("sample_long.csv", max_drawdown_stop=0.25, verbose=False)
print("前 3 筆成交：", [(d.date(), side, round(float(p), 2)) for d, side, p in broker.fills[:3]])

curve_no_stop, _ = run("sample_long.csv", max_drawdown_stop=1.0, verbose=False)
```

輸出：

```
⛔ 回撤 -28.6% 超過上限，系統停機，等待人工檢查
結束：最終資產 1,493,298，共成交 8 次
前 3 筆成交： [(datetime.date(2010, 10, 11), 'buy', 70.0), (datetime.date(2014, 7, 22), 'sell', 104.9), (datetime.date(2016, 1, 25), 'buy', 74.29)]
結束：最終資產 2,480,992，共成交 15 次
```

**兩個重點：**

| 觀察 | 說明 |
|---|---|
| **沒有停機開關**：最終 2,480,992 | 和 Phase 10 工具箱 `backtest()` 的結果（約 2,481,004）幾乎一樣，差異來自整數股——**交叉驗證通過** ✅（10.3） |
| **有停機開關**：2018 年回撤 −28.6% 時停機 | 之後系統不再交易，等待人工檢查；最終 1,493,298 |

> 🔑 **停機開關讓這個策略少賺了很多**——停機之後市場其實回升了。那它是壞東西嗎？不是。停機開關的目的**不是提高報酬**，而是在「**系統可能壞掉了**」時阻止損失繼續擴大：可能是程式 bug、資料錯誤、券商介面出問題、或策略真的失效了。人工檢查後，如果確認一切正常，可以重新啟動。
>
> 停機門檻要參考 11.5 的蒙地卡羅結果：設得太緊（例如低於 95% 信心的回撤），正常的回撤也會觸發停機；設得太鬆，就失去保護的意義。

### 4. ⚠️ 自動化系統常見的故障

| 故障 | 例子 | 預防方法 |
|---|---|---|
| **資料錯誤** | 資料源少了一天、價格多一個 0、除權息沒調整 | 資料檢查（9.10 的檢查清單）；異常時暫停 |
| **重複下單** | 程式重新啟動後，又送了一次同樣的委託 | 送單前檢查未成交委託與目前部位（骨架中的 `if self.pending`） |
| **部分成交、沒成交** | 限價單只成交一半；漲跌停買不到 | 每次都和券商**對帳**實際部位 |
| **網路或券商中斷** | 送單失敗、收不到成交回報 | 重試機制、警報、備用的手動下單方式 |
| **時間錯誤** | 時區、假日、提早收盤 | 使用交易所的交易日曆 |
| **金鑰外洩** | API 金鑰寫在程式裡，上傳到 GitHub | 金鑰放在環境變數或不上傳的檔案（9.14） |
| **策略失效** | 市場改變，策略開始持續虧損 | 停機開關、定期檢討（Phase 12～13） |

> 💡 自動化最大的風險，往往不是策略本身，而是**程式錯誤會被自動、快速、大量地執行**。手動交易時，你看到「買 10 萬張」會覺得不對勁；程式不會。

### 5. 自動化的程度

| 程度 | 做法 | 適合 |
|---|---|---|
| **半自動** | 程式每天收盤後產生「明天要做的委託清單」，**人工確認後**手動下單 | ⭐ **新手建議從這裡開始** |
| 自動下單 + 人工監控 | 程式自動下單，人每天檢查日誌與對帳 | 策略與程式都經過長時間驗證後 |
| 全自動 | 程式自動下單、監控、處理異常 | 專業團隊 |

> 🔑 Phase 12 的模擬交易，就可以用「半自動」的方式進行：用這個骨架程式的資料、訊號、風控模組，每天收盤後產生訊號，手動記錄或下單，並和程式的預期對照。

### 6. 從回測走向自動化的檢查清單

- [ ] 策略已通過 Phase 10 的完整檢驗，並完成回測報告
- [ ] 回測與實盤使用**同一套**資料與訊號程式
- [ ] 資料模組有完整的檢查，異常時會暫停
- [ ] 風控模組有部位上限、總風險上限、**停機開關**
- [ ] 下單模組能防止重複下單，並每天和券商對帳
- [ ] 所有動作都有日誌；異常時會發出警報（例如寄信或手機通知）
- [ ] API 金鑰不在程式碼中，也不在 Git 裡
- [ ] 先用**紙上交易**或**半自動**至少執行數個月（Phase 12）
- [ ] 有「系統壞掉時怎麼辦」的手動備案

## 📌 重點整理

1. 自動化系統 = **工廠生產線**：資料 → 訊號 → 風控 → 下單 → 監控。
2. 模組分開：回測與實盤**共用**資料與訊號程式，降低錯誤。
3. 骨架程式沒有停機開關時，結果和 Phase 10 回測一致（**交叉驗證**）。
4. **停機開關**的目的不是提高報酬，而是在系統可能壞掉時阻止損失擴大；門檻參考蒙地卡羅結果。
5. 常見故障：資料錯誤、重複下單、部分成交、斷線、時間錯誤、金鑰外洩、策略失效。
6. 新手從**半自動**開始：程式產生訊號，人工確認後下單。

## ❌ 常見誤解

| 誤解 | 事實 |
|---|---|
| 「自動化可以消除所有人為錯誤」 | 自動化會把程式錯誤快速、大量地執行；需要風控、監控與停機開關。 |
| 「停機開關會讓績效變差，不需要」 | 它的目的是在系統異常或策略失效時阻止損失擴大，不是提高報酬。 |
| 「回測程式和實盤程式可以分開寫」 | 分開寫容易造成兩者不一致；最好共用資料與訊號模組。 |
| 「接上券商 API 就可以全自動交易」 | 要先經過長時間的紙上交易與半自動驗證，並處理對帳、斷線、重複下單等問題。 |

## 🛠️ 練習（約 90 分鐘）

**練習 1：執行骨架程式**
下載 [`code/paper_trading_skeleton.py`](code/paper_trading_skeleton.py)，和 `sample_long.csv`、`bt_toolkit.py` 放在一起執行 `run()`。打開 `verbose=True`，閱讀日誌中的每一筆成交。

**練習 2：換策略**
新增一個 `RsiStrategy` 類別（8.5 的 RSI(2) 規則），替換 `MaStrategy`，其他模組完全不改，執行看看。這就是「模組分開」的好處。

**練習 3：加入資料檢查**
在 `DataFeed` 中加入檢查：如果今天的收盤價和昨天相差超過 15%，記錄一則警告，並讓 `run()` 當天不產生新訊號。用 9.11 的分割例子（價格突然變成四分之一）測試。

**練習 4：半自動模式**
修改 `run()`，讓它只處理資料到最後一天，並印出「明天要執行的委託」（買、賣或不動作）。這就是你在 Phase 12 每天收盤後要做的事。

## ✅ 自我測驗

**Q1. 自動化交易系統的五個模組是什麼？**

<details><summary>看答案</summary>

① 資料（取得、清理、檢查）；② 訊號（執行策略規則，產生目標部位）；③ 風控（部位上限、總風險、回撤上限與停機開關）；④ 下單（轉成委託、送出、確認成交、對帳）；⑤ 監控與紀錄（日誌、警報、報表）。

</details>

**Q2. 停機開關讓骨架程式的最終資產變少了，為什麼還需要它？**

<details><summary>看答案</summary>

停機開關的目的不是提高報酬，而是在帳戶回撤異常時（可能代表程式錯誤、資料錯誤、券商介面問題或策略失效）停止交易，避免損失繼續擴大，等待人工檢查。事後看可能少賺，但它保護的是「系統壞掉」時的極端風險。

</details>

**Q3. 為什麼新手建議從「半自動」開始？**

<details><summary>看答案</summary>

因為半自動由程式產生訊號、人工確認後下單，可以在每次下單前發現明顯錯誤（例如異常的數量或方向），同時驗證程式與策略在真實環境中的表現，累積經驗後再逐步提高自動化程度，降低程式錯誤被大量執行的風險。

</details>
